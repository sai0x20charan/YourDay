Data layer refactor plan for YourDay

A guide in simple English on why the current setup hurts the app and how to fix it step by step.

What is wrong right now

The app works on screen, but the code underneath has several bad habits that make bugs easy to write and hard to fix.

Problem What happens today Why it is bad
Repositories return booleans WeatherRepo.getCurrentForecast() returns Flow<ProcessState<Boolean>>. The repository fetches data, writes it to a file, and returns true. The screen must make two separate calls: one to ask for a fetch, and one to read the file.
DataStore used as a database The app converts whole weather objects and task lists into JSON text and dumps them into Android settings. Android preferences are built for tiny values like flags or strings. Rewriting entire weather reports to disk freezes and slows down reads.
Two conflicting preference stores UserPreferencesStore and DataStoreRepositoryImpl both touch the same keys. Logging out in one place writes an empty string, while the other screen expects null. The UI shows you are still logged in after you disconnect.
Screen does everything HomeScreenComponent handles network calls, tokens, GPS, and calendar checks in one giant file. If you want to show weather on another screen or run background sync, you have to copy and paste hundreds of lines.
Calendar queries block the UI CalenderEventsImp calls the Android calendar content resolver on the main thread. Phones with hundreds of calendar events will stutter or freeze when opening the home screen.

How the data flow should look

Good architecture has one clear direction for data: UI calls repositories, repositories grab data from network or cache, and data flows back to the screen as a steady stream.

Four rules for the new data layer

  1. A repository gives you data, not booleans. When the UI asks the weather repository for weather, it gets Flow<WeatherData> back.
  2. Keep DataStore for settings only. Keep temperature units, theme choices, and login tokens in DataStore. Keep live weather and tasks in memory or in a real database.
  3. One preference store for the whole project. Delete UserPreferencesStore. Let one clean class manage settings keys.
  4. Run disk and network work in the background. Database and calendar queries must use Dispatchers.IO so the UI never drops frames.

Code comparisons

1. Weather repository

Before: The function returns Boolean after saving to disk.

// Bad: WeatherRepo.kt
interface WeatherRepo {
    suspend fun getCurrentForecast(lat: Double, long: Double): Flow<ProcessState<Boolean>>
}

// In WeatherRepoImp.kt:
dataStoreRepo.setWeatherData(weatherData)
emit(ProcessState.Success(true))

After: The repository holds the latest weather and exposes it directly.

// Good: WeatherRepository.kt
interface WeatherRepository {
    val weatherData: StateFlow<WeatherData?>
    suspend fun refreshWeather(lat: Double, lon: Double): Result<Unit>
}

class WeatherRepositoryImpl(
    private val api: WeatherRemoteDataSource
) : WeatherRepository {
    private val _weatherData = MutableStateFlow<WeatherData?>(null)
    override val weatherData: StateFlow<WeatherData?> = _weatherData.asStateFlow()

    override suspend fun refreshWeather(lat: Double, lon: Double): Result<Unit> {
        return runCatching {
            val dto = api.getForecast(lat, lon)
            _weatherData.value = dto.toWeatherData()
        }
    }
}

2. Todoist task management

Before: The screen checks tokens, triggers network calls, and listens to DataStore.

// Bad: HomeScreenComponent.kt
dataStoreRepo.todoistAccessToken.collectLatest { token ->
    if (token != null) {
        fetchTodoistTasks(token)
    }
}

After: The repository handles the token and gives the screen clean task data.

// Good: TodoRepository.kt
interface TodoRepository {
    val tasks: Flow<List<TodoTask>>
    val isConnected: Flow<Boolean>
    suspend fun refreshTasks(): Result<Unit>
    suspend fun disconnect()
}

3. Calendar query on background thread

Before: Runs synchronously on the caller thread (which was Dispatchers.Main).

// Bad: CalenderEventsImp.kt
override fun getCalenderEvents(): List<CalenderItems> {
    val cursor = context.contentResolver.query(uri, projection, null, null, null)
    // runs on main thread
}

After: Suspend function running on Dispatchers.IO.

// Good: CalendarRepositoryImpl.kt
class CalendarRepositoryImpl(private val context: Context) : CalendarRepository {
    override suspend fun getTodayEvents(): List<CalendarItem> = withContext(Dispatchers.IO) {
        val cursor = context.contentResolver.query(uri, projection, null, null, null)
        // runs safely in background
    }
}

Step by step refactoring order

  1. Delete duplicate preference store: Remove UserPreferencesStore.kt. Merge its token and unit logic into a single UserPreferencesRepository.
  2. Fix calendar typo and threading: Rename Calender to Calendar. Wrap query calls in withContext(Dispatchers.IO).
  3. Remove JSON cache from DataStore: Remove WEATHER_DATA_KEY and TODO_DATA_KEY. Store live data in repository state flows.
  4. Update repository interfaces: Change repository methods from ProcessState<Boolean> to return data or Result<Unit>.
  5. Thin out HomeScreenComponent: Let the screen component observe data from repositories instead of micro-managing token checks and disk writes.
